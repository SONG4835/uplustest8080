# code-annotator: 초보자용 설명 주석 달기

지정된 코드 파일을 읽고, **코드는 한 글자도 바꾸지 않은 채** 초보자가 이해할 수 있는 한국어 주석을 파일에 직접 작성한다.

## 확정된 방침 (사용자와 합의됨)

- **언어**: 한국어
- **상세 수준**: "어려운 부분 위주". 파일 개요 + 함수/클래스 설명 + 복잡하거나 헷갈리는 로직만 상세히. 변수 선언, 단순 return 같은 쉬운 줄은 주석을 달지 않는다. (모든 줄에 달면 오히려 핵심이 묻혀 초보자가 읽기 힘들어진다.)
- **스타일**: ① *무엇을 하는지 + 왜 그렇게 짰는지* ② *쉬운 비유나 예시 값* 사용.
- **기존 주석**: 초보자용으로 **다시 작성**한다. 기존 주석이 더 어렵거나 부족하면 쉬운 설명으로 교체한다. 단, 아래 "건드리지 말 것" 항목은 예외.
- **산출물**: 지정한 원본 파일 자체에 주석이 추가된 상태. 별도 사본을 만들지 않는다.

## 절차

1. **대상 확인**: 사용자가 준 파일 경로를 확인한다. 파일을 지정하지 않았거나 여러 개로 모호하면 어떤 파일인지 되묻는다. 폴더를 주면 그 안의 코드 파일 목록을 보여주고 대상 확인을 받는다.
2. **전체 읽기**: Read로 파일 전체를 읽고, 언어(주석 문법)와 전체 흐름을 먼저 파악한다. 이해가 안 되는 부분은 추측해서 단정하지 말고, 호출하는 다른 파일을 찾아보거나 "~로 보인다"라고 표현한다. 틀린 설명은 주석이 없는 것보다 초보자에게 더 해롭다.
3. **백업**: 수정 전 원본을 스크래치패드(임시 폴더)에 복사해둔다. 이 프로젝트는 git이 없을 수 있어, 문제 시 되돌리고 검증 비교에 쓰기 위함이다.
4. **주석 설계**: 아래 "무엇에 주석을 달까"를 기준으로 달 위치를 정한다.
5. **편집**: Edit(또는 필요하면 Write)로 주석만 삽입/교체한다. 코드 줄은 그대로 둔다.
6. **검증**: 아래 "검증" 절차로 코드가 바뀌지 않았는지 확인한다.
7. **보고**: 어떤 부분에 주석을 달았는지 짧게 요약한다. (파일 내용 전체를 응답에 다시 붙이지 않는다.)

## 무엇에 주석을 달까

**반드시 달기**
- **파일 맨 위 개요**: 이 파일이 전체에서 맡은 역할, 주요 흐름을 3~6줄로 요약.
- **함수/클래스/컴포넌트**: 무슨 일을 하는지, 입력(매개변수)과 결과(반환값)가 무엇인지, 왜 필요한지. 언어 관례(docstring, JSDoc 등)가 있으면 그 형식을 쓴다.

**어려우면 달기** (초보자가 막힐 만한 곳)
- 정규식, 비트 연산, 삼항 연산 중첩, reduce/map/filter 체인, 람다
- 비동기(async/await, Promise, 콜백), 재귀, 클로저, 데코레이터, 제너레이터
- 이유를 알기 어려운 조건문, 매직 넘버, 우회 처리(workaround), 성능 최적화
- 프레임워크 특유의 개념(훅, 미들웨어, ORM 쿼리 등)

**달지 않기**
- `i += 1  # i에 1을 더한다`처럼 코드를 그대로 읽어주는 주석. 정보가 없다.

## 좋은 주석 쓰는 법

- **무엇 + 왜**: "목록을 정렬한다"보다 "최신 글이 위에 오도록 날짜 내림차순으로 정렬한다(화면에서 최신 글을 먼저 보여주려고)".
- **비유와 예시 값**: 추상 개념은 일상에 빗대고, 데이터 변환은 실제 값을 넣어 보여준다.
  ```python
  # 정규식: 이메일에서 '@' 앞부분(아이디)만 뽑는다.
  # 예) "hong@uplus.co.kr" -> "hong"
  ```
  ```js
  // reduce는 '누적 계산기'처럼 배열을 한 칸씩 돌며 값을 하나로 합친다.
  // 예) [1, 2, 3] -> 0+1=1, 1+2=3, 3+3=6 -> 결과 6
  ```
- **전문용어는 처음 나올 때 한 번 풀이**하고 이후엔 반복하지 않는다. (예: "콜백 = 나중에 실행해달라고 넘겨주는 함수")
- 존댓말 대신 간결한 평서체("~한다", "~이다")로 통일하고, 한 주석은 보통 1~3줄로 짧게. 길어지면 블록 주석으로 분리.
- 주석이 코드와 어긋나지 않게, 코드가 실제로 하는 동작만 설명한다.

## 기존 주석 처리

기존 주석은 초보자용 설명으로 다시 쓴다. 다만 **의미나 동작이 있는 주석은 그대로 보존**한다. 지우거나 고치면 프로그램이 달라지거나 도구가 깨진다.
- 셔뱅(`#!/usr/bin/env python`), 인코딩 선언(`# -*- coding: utf-8 -*-`)
- 린터/타입체커 지시어: `eslint-disable`, `# noqa`, `# type: ignore`, `@ts-ignore`, `// prettier-ignore`
- 라이선스/저작권 헤더, `TODO`/`FIXME` 담당자·이슈 번호 (원문 유지하고 그 아래에 쉬운 설명을 덧붙이는 정도는 가능)
- 도구가 읽는 주석: JSX/템플릿 지시어, `#region`, 조건부 컴파일, JSON 스키마 참조 등

## 언어별 주의

- 주석 문법을 파일 언어에 맞춘다(`#`, `//`, `/* */`, `<!-- -->`, `--` 등).
- **JSON처럼 주석을 지원하지 않는 형식**에는 주석을 넣지 않는다. 파일이 깨진다. 이 경우 사용자에게 알리고, 대안(별도 설명 `.md` 파일)을 제안한다.
- Python은 함수 설명에 docstring(`"""..."""`)을 쓰되, 기존 docstring 내용(특히 doctest)을 깨지 않게 주의한다.
- 들여쓰기에 의미가 있는 언어(Python, YAML)는 주석 줄의 들여쓰기를 주변 코드와 맞춘다.
- 줄 끝(인라인) 주석은 줄이 너무 길어지면 윗줄에 단독 주석으로 쓴다.

## 검증

주석 작업은 "코드는 그대로"가 가장 중요한 약속이다. 편집 후 반드시 확인한다.
1. 백업본과 비교해 **주석이 아닌 줄이 동일한지** 확인한다. (diff 결과에서 추가/삭제된 줄이 모두 주석인지 훑어본다.)
2. 가능하면 문법 검사를 돌린다. 예: Python `python -m py_compile 파일`, JS `node --check 파일`. 도구가 없으면 생략하고 눈으로 점검.
3. 코드가 바뀐 흔적이 있으면 즉시 백업에서 복구하고 다시 진행한다.
4. 검증 결과(통과/생략/문제)를 보고에 포함한다.

## 보고 형식

- 보존한 기존 주석이 있으면 그 사실
- 검증 결과
